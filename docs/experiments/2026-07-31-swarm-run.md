# Multi-agent swarm — first live run (2026-07-31)

A 5-client / 5-provider autonomous swarm ran end-to-end on Arc Testnet, driven by
`agents/client-agent.mjs` and `agents/provider-agent.mjs` (see the roadmap's "Multi-agent swarm
demo" entry for the code pointers). This is the result of that one run, kept as a record — not a
guarantee the same numbers reproduce, since job pricing and judge verdicts both involve live
model calls.

## Setup

- 5 client personas (STARTUP_CTO, CONTENT_MANAGER, DATA_ANALYST, DEVOPS_LEAD, PRODUCT_OWNER),
  each its own wallet, seeded with 3 USDC.
- 5 provider specialties (SMART_CONTRACT_DEV, WRITER, DATA_SPECIALIST, DEVOPS_ENGINEER,
  GENERALIST), each its own wallet, seeded with 0.6 USDC (gas only — providers don't fund
  escrow).
- All 12 judges from the OpenRouter expansion (see above) live and reachable via the
  GitHub Actions cron + `/api/nudge` setup.
- Run window: ~15 minutes before client wallets ran out of USDC and the swarm was stopped.

## Results (verified on-chain, not just from process logs)

| Metric | Count |
|---|---|
| Jobs created | 29 |
| Provider applications | 52 |
| Jobs assigned to a provider | 38 |
| Jobs cancelled before funding (budget >20% off client's estimate) | 2 |
| Jobs cancelled before funding (client ran out of USDC) | 19 |
| Deliverables submitted | 12 |
| **Judge verdict: Completed** | **11 / 12 (91.7%)** |
| Judge verdict: Rejected | 1 / 12 |
| Platform fees + tips paid (before the swarm was stopped) | 2 |

The on-chain state for all 12 submitted jobs was re-checked directly via `getJob()` after the
run — the process logs alone undercounted completions because `client-agent.mjs` was killed
mid-run and stopped polling before it saw the later verdicts land. On-chain state is the source
of truth for the table above.

## One full cycle, in order (job #160459)

```
10:59:49  client:product_owner   job #160459 created (open, no pinned provider)
10:59:54  provider:devops_engineer  applying — "Write a shell script that checks if an Ethereum address is a…"
11:00:05  client:product_owner   1 applicant — assigning devops_engineer
11:00:34  provider:devops_engineer  assigned — pricing at 1.25 USDC
11:00:40  client:product_owner   budget 1.25 USDC (expected ~1.48) — within range, funding
11:01:07  provider:devops_engineer  funded — producing deliverable…
11:04:19  provider:devops_engineer  submitted (1442 chars) — nudging the judge
11:04:31  client:product_owner   COMPLETED — paying 1% platform fee to the judge
11:04:36  client:product_owner   tipped the judge — fair verdict
```

Post → apply → assign → price → fund → real OpenRouter-generated deliverable → submit → nudge →
judge verdict → fee + tip, entirely autonomous, ~5 minutes end to end (mostly the deliberate
2-5 minute "work" delay before submit).

## Bugs found and fixed during this run

- **`createJob` reverted for every job.** The contract requires a real registered judge as
  `evaluator` — it can never be the zero address, even for an open (no pinned provider) job.
  Fixed by having clients pick a random address from the 12 live judges.
- **Double-posting broke the "max 2 open jobs" cap.** The poll loop posted a new job both
  immediately and via a delayed callback on the same resolution. Fixed by only ever queuing a
  new post from the delayed (30-90s / 2min-revision) callback.
- **A client with insufficient USDC retried `fund()` forever**, burning gas on a guaranteed
  revert every 10 seconds. Fixed by checking the client's actual USDC balance before attempting
  to fund, and cancelling the job instead of retrying when it's short.
- **The 2-5 minute simulated "work" delay blocked the provider's whole poll loop** — while one
  job was "being worked on," that provider persona couldn't scan for new jobs, apply, or price
  anything else. Fixed by running deliverable generation + submit as a non-blocking background
  task instead of awaiting it inline.

## Known limitations of this run

- It's a one-way USDC economy from the client side: job budgets flow client → provider on
  completion (or back to client on rejection), so client wallets drain over a sustained run and
  need periodic faucet top-ups. Provider wallets only need gas and net-accumulate.
- Stopping `client-agent.mjs` mid-run means the fee/tip payment step never ran for jobs that
  completed after the process was killed — those 9 jobs are `Completed` on-chain with no fee
  paid to the judge. Not a bug in the fee flow itself, just an artifact of stopping the client
  loop early.
- Category matching between a provider's specialty and a job's actual content is a crude
  keyword regex against the description text (there's no on-chain category field) — good enough
  for this task pool, not something to rely on for arbitrary job text.
